A change that keeps the values and changes quantity ids, evidence references or lineage (the kind of drift a snapshot rekey causes, which is what the Lot16 1215 work had to declare) would pass. Please assert the pinned fingerprints, which are already known: Lot16 `ef58f8ae1a963a5b985edfa6dda752f3f338d9d5c42d56969b0e86f538aadfeb` and Maryborough `9f3ab9ac1497cae5c29f8873af9287a5d6e3b3a386937fdeb37f8b5989fd780d` (the latter is already asserted in `score-gpt3-maryborough-exact-24.yml`). A deliberate change then needs a deliberate, separately reviewed edit of the pin.
2. *Cost / duplication.* It runs both full original-source producers a third time per production push (about 25 minutes). The two existing replay workflows (`score-gpt3-lot16-1215-opening-local.yml`, `test-gpt3-maryborough-original-floor-score-input.yml`) already run the same two producers and now trigger on the whole import closure (#2787). Adding the fingerprint pin and the id-set assertion **inside those two workflows** gives the same protection at zero extra runtime; if a single combined job is wanted for the release, it should replace rather than add to them. (Measured duplication analysis: `docs/engineering/claude_handoff_2026-10-15/ci_replay_duplication_analysis_20261015.md` on #2789.)
3. *Trigger coverage.* `paths` lists `pb_*.py` and the two producer tools, but the static import closure of those two producers (204 files, computed with #2787's own helper) also contains three tools that are not in the filter: `tools/diag_gpt2_room_measurement_gates.py`, `tools/diag_gpt3_maryborough_floor_customer_gate.py` and `tools/diag_lot16_room_face_scope.py`, so an edit to any of them would not trigger this gate. #2787's closure test is the right mechanism - add this workflow and its two entry points to its replay table so the filter cannot drift.
