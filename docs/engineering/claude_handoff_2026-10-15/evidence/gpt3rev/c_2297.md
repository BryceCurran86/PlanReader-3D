**Consequences / precise upstream records needed (a sidecar must be *derived from these in the same producer process*, never inferred from labels, page ids or PDF hashes):**
1. Floor-area family: `LiveCanonicalRoomObject` (`canonical_room_id`, `snapshot_id`, `decision_scope_id`, `source_room_face_record_id`) joined to `LiveCanonicalFloorSurfaceObject` by `room_entity_id`, and to the W5 `SourceRoomFaceRecord.record_id`; the floor already asserts `room.snapshot_id == floor.snapshot_id` (`pb_live_canonical_floor_surface.py:291-292`). The sidecar record per quantity should carry {quantity_id, canonical_floor_id, canonical_room_id, source_room_face_record_id, snapshot_id, decision_scope_id, viewport_id} and a fingerprint over them.
2. Opening family: the `PhysicalOpeningAuthority` record (snapshot_id) plus the W4 scope result it was bound to (decision_scope_id, viewport_id) - the opening record does not carry the scope id itself, so the join must be producer-owned (selector key), not coordinate-based.
3. Floor-finish/ceiling: `support_snapshot_id` exists for finish; ceiling quantity publication has neither - needs the same room join.
4. Keep v1 payload/fingerprint untouched; the sidecar is a separate versioned receipt verified against the live producer objects, with rejection of: missing id, id reuse across quantities, conflicting scope for one face record, stale superseded snapshot (a newer derived generation of the same revision), same-label/different-scope rooms.

**Important lineage hazard for the design:** derived snapshot generations (`from_authenticated_viewports`, `from_source_visibility_producer` ...) change `snapshot_id` for the same revision; any verifier must compare against the generation that produced the room/face record, not "latest published". I hit exactly this in a probe (selectors built against the pre-producer snapshot returned zero scopes).
